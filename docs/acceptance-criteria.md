# Acceptance criteria and evidence

Release target: credential-free Go development service and the through frontend. Reviewed October 28, 2026, America/Los_Angeles.

Use **Verified** only when the named check has evidence. **Implemented, unverified** means code exists without completed verification. **Placeholder** means intentionally simulated external behavior. **Open** is missing or unresolved. A passing unit test does not substitute for an end-to-end provider test or an operational recovery exercise.

## Pilot blockers: external and operational gates

| ID | Gate | Required evidence | Current status |
|---|---|---|---|
| P01 | Real through identity | Verified identity provider with enrollment/recovery, MFA, immutable subject binding, session revocation, and outage handling | Placeholder; blocks real identities |
| P02 | Tenant administration | Real invitation acceptance, owner/admin/member assignment, last-owner protection, offboarding, and support recovery; no email-based auto-joining | Open; blocks shared customer workspaces |
| P03 | Protected vault/browser integration | One supported agent and site; real same-tab origin verification; secrets absent from model/tool logs, screenshots, snapshots, and concurrent observers; post-login state verified | Placeholder; blocks real credentials |
| P04 | Agent and device identity | Authenticated adapter/device, scoped permission, key rotation/revocation, and proof that caller-supplied tab/agent strings cannot impersonate the runtime | Placeholder; blocks remote agent access |
| P05 | Challenged or uncertain login | Human-required MFA, passkey, CAPTCHA, redirect, and ambiguous-result handling with no blind credential retry; original task can resume or explain why it cannot | Placeholder; blocks unattended claims |
| P06 | Disaster recovery | Encrypted backup, clean restore, migration/rollback rehearsal, tenant and audit reconciliation, measured RPO/RTO, revoked sessions not reactivated | Open — isolated synthetic dump/restore exercised; encryption, operating procedure, measured recovery targets, and full rehearsal not proven |

| P08 | Data lifecycle | Implemented retention and deletion, customer export, backup expiry, documented data map and subprocessor boundaries appropriate to chosen providers | Open; blocks real data retention claims |
| P09 | Deployment security | TLS/ingress configuration, restricted runtime database role, encryption/secret management, vulnerability review, independent security testing, and signed release approval | Open; blocks public production |
| P10 | Enterprise federation | Verified SSO and provisioning/offboarding for the target customer's provider; no unsupported success states | Placeholder; required before claiming SSO/SCIM support |

## Test data and failure recovery

Use two synthetic tenant identities and fictional provider account references. Do not type real provider passwords or OTP seeds into any demo. Verify failures through the public HTTP contract and persisted database state, not by checking UI text alone.

For network failure, keep the account selection and let the user retry. For an expired through session, clear stale client state and return to login. For a denied or revoked grant, show the reason and require new authorization. For an uncertain external fill, record the outcome as unknown/action-required; do not infer success from an HTTP 200 or automatically submit credentials again.

## Evidence log

The independent source review checked the backend configuration, HTTP handlers/middleware, schema/migrations, PostgreSQL store, test files, client mode/transport, and the login, home, accounts, activity, and use-case components. Source evidence supports the implementation statuses above. Test and browser execution was performed by the root and backend agents, not by this document reviewer.

Corrections from review were applied: actor/session idempotency fingerprint and migration, mixed-scheme Origin rejection, typed expired/exhausted challenge errors, Activity target visibility, friendly session labels, and Activity 401 redirection. Database regression tests passed; the root verified Activity labels after rebuilding and forced challenge/session expiry through the browser.

Audit entries currently describe successful state changes only. They have no outcome field or request-ID correlation and do not retain denied attempts. Application logs provide request IDs/statuses, but are not a durable tenant security audit. Record that limitation even if functional tests pass.

Runtime evidence reported by the root agent on October 28, 2026:

- `NEXT_PUBLIC_API_MODE=service npm run build` passed. This verifies the service-mode frontend build, not a hosted API deployment.
- `npm audit --omit=dev` found no production dependency vulnerabilities. The Go runtime and dependencies were updated to Go 1.27.3, pgx 5.9.2, and current indirect versions after the initial scan; the backend agent reported the subsequent `govulncheck` run passed with zero findings.
- Browser against the actual Go/PostgreSQL service: incorrect code showed feedback; `0000` signed in; Linear/Codex account creation, simulated handoff, pause disabling Test, reload persistence, resume, and Activity worked.
- Stopping the Go process and refreshing showed a connection error with Try again. There was no browser-demo fallback.
- Stopping PostgreSQL returned 503 from `/readyz` while `/healthz` remained 200; restarting PostgreSQL restored readiness to 200.
- Restarting the Go service retained the browser session, connected account, and audit history. After rebuilding, Activity showed account/agent targets and readable sign-in/out labels.
- Forced synthetic session expiry redirected to login. Forced challenge expiry showed its typed error, disabled the submit action, and offered Start again; that recovery completed successfully.
- Login, accounts, and Activity were inspected at 390 and 320 px with no horizontal overflow. Public use-case playback completed at 320 px, its signed-in illustration remained contained, and the dark desktop version was reviewed at 1280 px. Keyboard account selection, session logout, and dismissal/refresh of the connection form were checked. This is targeted UI verification, not a complete accessibility audit.
- A fresh `pg_dump`/restore into an isolated development database recovered one synthetic account, one handoff, and five audit events. Sessions and challenges were cleared in the restored copy and verified as zero. This is not an encrypted-backup, RPO/RTO, or production recovery certification.

## Release decision

**Current decision: the credential-free development sandbox is validated for local delivery within the recorded scope.** External integrations remain deliberate placeholders. Docker/Compose execution, hosted CI, a full accessibility audit, and a real customer pilot are not claimed. Static-preview publication is a separate frontend artifact and does not deploy the Go/PostgreSQL service. The customer pilot remains blocked by the provider and operational gates above; no production-ready or certification claim is approved.

## October 29 update: pricing and user settings

Added a separate `/pricing` page with explicitly proposed USD plans and no billing/checkout integration. Signed-in navigation now exposes `/settings`; sign-out is available there. Settings includes an optional display name, synchronized System/Light/Dark appearance, the free-preview plan, and development sign-in status. In Go mode it can revoke all of the current user's other sessions while preserving this session; the browser-only demo does not show a fake remote-session control.

Migration 003 persists display names. Profile editing and session revocation require the existing Origin and CSRF protections. Every authenticated role may edit its own profile; user identity comes from the current server session. Display names are limited to 80 Unicode code points, reject control characters, and are omitted from audit metadata. Cross-workspace session revocation is user-scoped and serialized; the current session is revalidated inside the transaction.

Verification: both frontend modes built, TypeScript passed, and real PostgreSQL tests passed with `go test -race -count=1 ./...` plus `go vet ./...`. Six new integration tests cover Unicode validation, persistence, roles, user isolation, concurrent revocation, HTTP boundaries, and audit-failure rollback. Browser checks covered profile save/reload in both modes, System selection by keyboard, header/theme synchronization, 320 px light and desktop dark layouts, authentication redirect, one additional session revoked through Settings, preservation of the current session, and sign-out. The production build browser console had no errors during the settings check. Billing and real MFA remain unconnected.
